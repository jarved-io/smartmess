# Smart Mess – meal-demand forecasting (XGBoost)

Predicts **how many meals a mess must prepare** for `mess × date × meal period` (target `served_meals`).
It does **not** predict individual students, rice, vegetables or ingredients. The safety buffer is a
configurable business rule applied *after* the prediction (`SAFETY_BUFFER`, default 2 %).

> Everything in `reports/EXAMPLE_SYNTHETIC_*` comes from **synthetic** data generated by `src/synthetic.py`.
> Those numbers prove the code runs, not that the model is accurate. Real accuracy = whatever
> `python -m src.train` reports on your real dataset.

Additions to your suggested structure: `history.py` (keeps DB access out of ML code), `feedback.py`
(feedback loop), `synthetic.py` (clearly labelled test data), `reports/` (training output separate from models).

## Dataset schema
| Column | Required | Notes |
|---|---|---|
| `date` | yes | YYYY-MM-DD |
| `mess_id` | yes | e.g. `south` |
| `meal_type` | yes | breakfast / lunch / dinner … |
| `served_meals` | yes | aggregate count (PRD's `mess_usage.served_count` is auto-renamed) |
| `active_students` | optional | headcount as known *before* the meal |
| `approved_leave` | optional | approved leave **as known before the meal** (see leakage note) |
| `is_holiday`, `is_event` | optional | 0/1; or pass a calendar file (`date,is_holiday,is_event`) |

One row per mess × date × meal. Missing optional columns simply drop the features that need them.
Other column names: add them to `COLUMN_ALIASES` in `config.py`.

## Quick start
```bash
cd ml && pip install -r requirements.txt

python -m src.synthetic && python -m src.train --data data/raw/SYNTHETIC_meal_history.csv --data-label synthetic   # dev only
```

## Design decisions
**Preprocessing** (every removal is counted in `data_quality.json`): exact duplicates dropped; invalid dates,
missing/negative targets dropped and counted; duplicate mess×date×meal keys keep the last record; non-numeric
values coerced to NaN and counted; missing `is_holiday/is_event` = ordinary day (assumption); `active_students`
carried forward within a mess; **outliers are flagged, never deleted** (a legitimately low day, e.g. a strike, is
information). A warning fires if >5 % of rows are removed. Missing calendar days stay missing (shifts are by calendar day).

**Leakage.** Every lag/rolling feature is computed on the target shifted by one day. `assert_no_leakage` overwrites all
targets on/after a date with 1e9, rebuilds, and requires earlier rows' features to be identical; training aborts if not.
Prediction appends a NaN-target placeholder row and uses the same code path (no train/serve skew).
*You must still verify:* `active_students` and `approved_leave` in your history must be the values known **before**
the meal, not back-filled afterwards (e.g. leave "approved" retroactively, or headcount computed from who scanned).
If `active_students` is really derived from that day's scans, drop the column.

**Why chronological splits.** Meal demand drifts (term start, exams, headcount). Random splits let the model train on
days after the ones it is tested on, which inflates accuracy. Split is by unique date: oldest 70 % train, next 15 %
validation (early stopping, prediction range), newest 15 % test (touched once). With ≥180 days an expanding-window
CV is also reported. The production model reuses the same hyper-parameters and iteration count, refit on all data;
the reported metrics are from the train-only model.

**Baseline gate.** Report compares XGBoost with the 7-day average (and same-weekday-last-week). If XGBoost does not
beat the 7-day average on test MAE, `metadata.mode = "baseline"` and the API serves the baseline
(`REQUIRE_XGB_BEATS_BASELINE=0` to override). **Cold start:** fewer than `MIN_TRAIN_DAYS` (90) days → no XGBoost is
trained, baseline only; at predict time a mess/meal with <`MIN_HISTORY_DAYS` (14) days, or an unseen mess, also uses
the baseline. A mess with no history at all returns HTTP 422 unless you deliberately set `DEFAULT_PARTICIPATION_RATE`.

**Metrics.** MAE primary (average meals wrong), RMSE secondary, bias (+ = over-forecast), R², and MAPE only when no
actual is zero. Plain-language summary is written into `report.md`. `prediction_range` is the 10th–90th percentile of
validation residuals (≈80 % empirical band, not a guarantee).

**Explainability.** `3_feature_importance.png` (gain); `pip install shap` adds a SHAP summary. Read these as "influential
in the model's predictions", not as causes of demand.

## API
| Endpoint | Purpose |
|---|---|
| `GET /health` | status, loaded version, mode |
| `GET /model-info` | version, mode, data label, metrics, features |
| `POST /predict` | `{mess_id,date,meal_type,active_students?,approved_leave?,is_holiday?,is_event?,safety_buffer?}` → `predicted_meals, recommended_preparation, prediction_range, model_version, method, warnings` |
| `POST /evaluate-forecasts` | `[{forecast_id,predicted_count,actual_count}]` → abs/squared errors for `forecast_evaluations` + MAE/RMSE + `retrain_recommended` |
| `POST /retrain` | retrain from the configured history source and hot-swap the model |

Set `ML_API_KEY`; Next.js sends it as `X-API-Key`. `recommended_preparation = round(predicted × (1 + buffer))`.

## Connecting to Next.js
1. Deploy the service (Render/Railway/Fly: `pip install -r requirements.txt`, start `uvicorn api.app:app --host 0.0.0.0 --port $PORT`). Set env vars from `.env.example`.
2. Data: either upload a CSV (`HISTORY_SOURCE=csv`) or `HISTORY_SOURCE=postgres` with a **read-only** `DATABASE_URL` and `pip install sqlalchemy psycopg2-binary`. Default query reads `mess_usage(mess_id,date,meal_type,served_count)`; override with `HISTORY_SQL` to add `active_students`, `approved_leave`, etc.
3. In `apps/web/.env.local`: `ML_SERVICE_URL=https://your-ml-host` and `ML_API_KEY=...` (server-side only, never `NEXT_PUBLIC_`).
4. Route handler `apps/web/app/api/forecasts/route.ts`:
```ts
export async function POST(req: Request) {
  const body = await req.json(); // {mess_id,date,meal_type,active_students,approved_leave}
  const r = await fetch(`${process.env.ML_SERVICE_URL}/predict`, {
    method: "POST",
    headers: { "Content-Type": "application/json", "X-API-Key": process.env.ML_API_KEY! },
    body: JSON.stringify(body),
    cache: "no-store",
  });
  const data = await r.json();
  if (!r.ok) return Response.json(data, { status: r.status });
  // persist into `forecasts`: predicted_count, range (low/high), model_version
  return Response.json(data);
}
```
5. Feedback loop: nightly (or when `POST /api/mess-usage/actual` is called) join `forecasts` with `mess_usage.served_count`, POST the pairs to `/evaluate-forecasts`, store the returned errors in `forecast_evaluations`. Show the MAE trend on the dashboard. When `retrain_recommended` is true (or weekly), call `/retrain`; versions increment `xgb_v2, xgb_v3…` and every forecast stores its `model_version`.

## Limits to keep honest
* Forecast horizon is day-ahead; the latest actuals should be in the database (the API warns if the newest actual is >1 day old).
* Holiday/event flags must be supplied for future dates; the model cannot guess them.
* Seasonal patterns longer than a year cannot be learned from <1 year of data.
